# Lossless BF16-to-F32 GEMV fixture results (2026-10-15)

## Scope and provenance

This is an operator microfixture, not a model benchmark. It uses the complete packed BF16 `output_hc_down.weight` and `output_hc_up.weight` tensors from the configured IQ3_XXS GGUF, a fixed synthetic F32 activation batch of 8 columns, and a one-node GGML `MUL_MAT` graph. All three arms use the same activation values and exact same weight values after BF16 decoding.

Runtime: `runtime-perf-v14e`, linked through `LD_LIBRARY_PATH=$R/lib`. `libggml-cuda.so.0` SHA256 `c3c680ee0085e6ecac6604b58ae69d29be3b717cd93fdf3a5cba7e22f3a28f72`; `libggml-base.so.0` SHA256 `aa2ccdbab0a5a354d64f33d325c8dd74e6f1c8ffdf854e1c1e8fe98c428cda26`. `ldd` with the locked runtime path resolves all ggml libraries under `runtime-perf-v14e/lib`. Fixture binary SHA256 `316bfd4f69c31e690a4b519a8d86ac17b818d907b2c18acfd051659b52f87109`.

Only physical GPU2 was visible during the bounded CUDA runs. The CUDA graph optimization flag was enabled; path logs show capture and replay for both shapes in all arms.

## Real tensor selection

The configured GGUF metadata was read without materializing the model weights. Only these two 6.25 MiB raw tensors were then read from their recorded GGUF offsets:

| Tensor | GGML dimensions `[K,N]` | BF16 bytes | GGUF data offset |
|---|---:|---:|---:|
| `output_hc_down.weight` | `[10240,320]` | 6,553,600 | 448,069,568 |
| `output_hc_up.weight` | `[320,10240]` | 6,553,600 | 454,664,128 |

Each BF16 tensor was expanded to F32 with the exact high-16-bit representation. All 6,553,600 values round-tripped bit-for-bit. The two F32 weights occupy 25 MiB; replacing the BF16 tensors would add 12.5 MiB, while retaining both representations would add 25 MiB.

## Steady graph-replay results

Median/p90 wall time measures `ggml_backend_sched_graph_compute` plus synchronization over 12 warmed graph replays. It is an operator-level measurement, not a kernel-only profile or full-model gain.

| Shape | Custom BF16 GEMV | Stock BF16 MMVF | Expanded F32 MMVF | F32 vs stock | Custom vs stock |
|---|---:|---:|---:|---:|---:|
| Down, K=10240 N=320 B=8 | 0.047533 / 0.047873 ms | 0.063444 / 0.064394 ms | 0.055964 / 0.057213 ms | 11.8% faster | 25.1% faster |
| Up, K=320 N=10240 B=8 | 0.079230 / 0.079399 ms | 0.120696 / 0.121126 ms | 0.100188 / 0.102898 ms | 17.0% faster | 34.3% faster |

Routes were confirmed as follows: `GGML_SM70_BF16_GEMV=2` emitted `sm70_bf16_gemv` with the exact tested K/N/B shapes; `=0` forced the stock BF16 path; the F32 arm used an F32 weight tensor and the ordinary F32 MMVF branch. The source guard for the tested shapes is `K >= 10240` or `N >= 8192` with `ncols >= 5`; the fixture uses `ncols=8`.

## Numerical results

- BF16-to-F32 weight expansion: exact for all 6,553,600 weight elements.
- Stock BF16 vs expanded F32 output: bitwise identical for both shapes: 2,560/2,560 down outputs and 81,920/81,920 up outputs; max absolute difference 0, NRMSE 0.
- Custom BF16 vs stock BF16: down max absolute difference `1.1920929e-7`, NRMSE `2.08646e-7`; up max absolute difference `2.9802322e-8`, NRMSE `1.14498e-7`. This small difference is consistent with the custom kernel's FMA/tree reduction order. It does not indicate a change in BF16 weight values.
- The independent sequential-FMA CPU reference was also emitted for each shape; raw metrics are in each run log.

## One-time expansion vs steady work

The CPU preparation script read 12.5 MiB of selected BF16 weights, wrote 25 MiB of F32 weights, and verified exact round-trip in `0.462 s` wall time on this warm local-file run. This measures only the two output-HC matrices, not conversion of every eligible model tensor. The steady replay timings above exclude this preparation. The fixture uploaded each weight before graph capture, but did not separately time the GPU upload or a full-model cache build.

## Projected cache budget

The GGUF metadata inventory has 486 BF16 tensors totaling 1,531,166,720 bytes (1.426 GiB). Applying the current dispatch shape guards and assuming the relevant op has 8 columns gives an upper-bound eligible set of 291 tensors / 1,331,691,520 BF16 bytes (1.240 GiB):

- `[K=10240,N=320]`: 97 tensors, 635,699,200 bytes.
- `[K=320,N=10240]`: 97 tensors, 635,699,200 bytes.
- `[K=10240,N=4]`: 96 tensors, 7,864,320 bytes.
- PLE key `[K=2560,N=10240]`: 1 tensor, 52,428,800 bytes; it may remain CPU-resident, so including it is conservative for a GPU cache.

With even six-way sharding, replacing only the eligible BF16 storage with F32 adds about 0.207 GiB (212 MiB) per GPU on average. Keeping BF16 weights plus a separate F32 side cache adds about 0.413 GiB (423 MiB) per GPU on average. Replacing every BF16 tensor would add about 0.238 GiB per GPU; retaining a full F32 side cache would add about 0.475 GiB per GPU. These are uniform averages only; actual placement, replicated tensors, graph workspace, and per-card headroom need model-level accounting before integration. Earlier in this task, an active V14e snapshot reported 15.2–15.4 GiB used out of 16,128 MiB; that is not a current V14f fit guarantee.

## Source and cache-hook audit

- The active custom dispatcher calls `gemv_sm70_bf16_launch_generic` on `src0->data` directly in `ggml-cuda.cu:2694-2705`; there is no converted weight cache in this path.
- `kernel_sm70_bf16.cuh:197-205` loads the original BF16 row as vectorized `uint4`, then converts values to F32 registers for accumulation. The custom path is dispatched during the matrix operation and performs no persistent weight preparation.
- `ggml_cuda_should_use_mmvf` selects stock BF16/F32 MMVF for the tested V100 shapes (`mmvf.cu:1020-1038` and following type cases). The stock and expanded-F32 outputs matched exactly.
- Searches found BF16 conversion helpers for communication/op scratch (including AllReduce), but no reusable persistent BF16-to-F32 weight-cache preparation hook outside graph capture. Any F32 side cache would need to be allocated/populated during model load or reserve, before CUDA Graph capture; lazy allocation in the op dispatch should not be introduced.

## Decision

For these two real hot output-HC matrices, a lossless F32 cache beats stock BF16 MMVF by 11.8–17.0%, but the existing custom BF16 GEMV is still 17.7–26.4% faster than the F32 arm and uses half the weight bandwidth/storage. The F32 cache is therefore not a better default route than the existing custom kernel for these shapes. Its useful role is as an exact stock-path control or fallback candidate; do not project its operator gain to the whole model without full-model timing and memory accounting.
