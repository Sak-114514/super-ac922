# MTP D2 fixed-prefix lane generalization readiness

Date: 2026-10-15  
Scope: read-only audit of the private `standard-opt-20261014` source, the common fixed-prefix planner, and the existing P4 `dual-context-runner.cpp`. No engine edit, build, model load, or GPU work was performed for this note.

## Verdict

- D2 unrolling and the six-row-per-lane fixed-prefix route already exist, but the combined path is currently gated to **exactly four lanes** in both the common dispatcher and `llama_context`.
- The P4 runner's `n_parallel=2`, `draft.n_max=2`, two-bank plan has **two lanes per speculative context**, not four. The two banks have separate `common_speculative_impl_draft_mtp` instances; their lane counts are never added together. With the current source, this plan does not arm the D2 unrolled graph and therefore does not consume fixed-prefix padding in that graph.
- Existing multi-lane storage, step layout, token packing, and end-of-chain reorder are already lane-variable up to eight. The blocker is a small set of explicit four-lane checks and the fixed-prefix planner's four-lane contract, plus the backend shape probe that is written for four outputs.
- Source has no identifier or environment variable literally called `newdeepguard`. The relevant separate guards are the catch-up row cap, the Qwen4Exp/MTP architecture restrictions, the six-row fixed-prefix validity checks, and the explicit rollback path that forbids padded rows from falling through into the legacy chain.

## Fixed-prefix and rollback invariants to preserve

`LLAMA_MTP_FIXED_PREFIX_ROWS=6` means six rows **per active lane**: up to five real catch-up rows plus the seed, with dummy rows used only to fill the graph input. The planner must continue to require contiguous source positions, exactly one output seed per lane, no extra future source row, unique sequence lanes, context-safe positions, and enough `min(n_ubatch,n_batch)` rows. Those checks are in `mtp-fixed-prefix-plan.h:108-175` and `common/speculative.cpp:2178-2244`.

After planning, `common/speculative.cpp:2211-2232` shifts each lane's real `first_pos`, constructs the padded lane-major batch, and retains the original catch-up/seed snapshot. `llama_context::process_ubatch_mtp_unrolled()` snapshots depth-0 KV indices/mask before removing future dummy rows and then reserves each dependent depth separately (`llama-context.cpp:2760-2824`). If fixed-prefix planning succeeds but the graph is unavailable, `common/speculative.cpp:2432-2438` aborts, rolls back to each real `first_pos`, restores the original batch, and uses generic MTP. Do not weaken this path or allow synthetic rows to enter the per-depth fallback.

## Other guards that are not lane-count gates

- The unrolled context is Qwen4Exp MTP only, GPU argmax only, no samplers, no pipeline parallel, masked/unmasked nextn embeddings active, no MoE cache, one MTP block, and no DSV4 compression on that block (`llama-context.cpp:2102-2109`; the model graph separately asserts one Qwen4Exp MTP block at `qwen4exp.cpp:646-648`). Preserve these guards for 2/3 lanes.
- The multi-lane route itself is eligible for `n_seq=2..8`, one-head/non-shared-memory MTP, greedy/no backend sampler, non-adaptive mode, and `n_max<=32` (`common/speculative.cpp:1630-1646`). `LLAMA_MTP_GPU_CHAIN_MULTI=1` also implies sequence layout/fold activation (`:1575-1586`). These gates already include 2/3 lanes.
- The catch-up guard is `LLAMA_MTP_GPU_CHAIN_MULTI_MAX_CATCHUP`; default `-1` allows any catch-up count (`common/speculative.cpp:2080-2086`, `src/src/llama-mtp-chain-layout.h:138-140`). Fixed-prefix planning then imposes its own per-lane maximum of five catch-up rows and total fixed-row budget. If “newdeepguard” refers to this guard, it is independent of lane count.
- P4 `dual-context-runner.cpp:61-81,263-296` sets D2 (`draft.n_max=2`), two lanes per bank (`p.n_parallel=2`), and two independent banks. It also sets `cp.n_rs_seq=max(spec.need_n_rs_seq(),4)` at `:69`; `need_n_rs_seq()` returns D2's `draft.n_max` (`common/common.h:396-402`), while `n_rs_seq` is recurrent-state rollback capacity (`src/src/llama-cparams.h:19` and Qwen4Exp's `n_rs_seq+1` state slots at `qwen4exp.cpp:3229-3250,3354-3372`). Keep the runner's four rollback slots unchanged; it is not a four-lane requirement.

## Smallest generalization slice

1. Make the fixed-prefix helper accept the explicitly supported lane set `{2,3,4}` (rather than broadening directly to all eight), while keeping `rows_per_lane=6`, `n_outputs=lanes`, row budget `lanes × 6`, and all existing source/seed/position checks. The existing planner test currently asserts that three lanes must be rejected (`fixtures/mtp-fixed-prefix-pad-20261015/planner-test.cpp:111-112`); replace that assertion with 2- and 3-lane positive cases and keep rejection cases for unsupported counts, insufficient row budgets, unequal/invalid rows, and context overflow.
2. Change the common `unroll_shape` lane gate (`speculative.cpp:2124-2126`) and context `enable_mtp_gpu_chain_multi_unrolled()` lane gate, minimum ubatch, prefix row bound, and backend shape probe (`llama-context.cpp:2102-2147`) to use the active lane count. The probe's step-0 token tensor, dependent-step token tensor, and history view are currently fixed to 4 (`:2142-2147`).
3. Keep six rows per lane in `process_ubatch_mtp_unrolled()`; replace only the `lanes != 4` rejection and its fixed-four log (`llama-context.cpp:2750-2755,2887-2889`). Require `n_ubatch,n_batch >= 6 × lanes` only for fixed-prefix mode; the current `24` cap is `4 × 6`.
4. In Qwen4Exp's graph constructor, remove the per-step `n_outputs == 4` assert (`qwen4exp.cpp:863`) in favor of a single derived lane count and equality checks across all steps. Its `count = lanes × depth`, concat, history view, and token packing are already variable (`:900-912`).
5. Preserve the two-bank runner's per-context isolation and the current semantic/rollback gates. Do not treat two banks × two lanes as four lanes inside a Meta context; each bank's speculative object receives `n_seq=2`.

## Can the original 2-bank × 2-lane P4 plan use D2 + fixed prefix?

**Not with the current source.** Each bank initializes its own `common_speculative_impl_draft_mtp` with `n_seq=params.n_parallel=2` (`dual-context-runner.cpp:74-79,276-286`). The common four-lane `unroll_shape` test rejects it before fixed-prefix planning, and `llama_context::enable_mtp_gpu_chain_multi_unrolled()` repeats that rejection. The two banks' four total requests do not combine into one four-lane graph.

**After only the lane-shape generalization above, it is the right first candidate.** The P4 runner has `n_batch=n_ubatch=512`; a two-lane six-row prefix uses 12 input rows per bank, within those budgets. Its existing D2, per-bank separate contexts, memory reset, carry reset, async bank submit/collect, and expected-output semantic checks provide the needed interface. The environment for the candidate must set `LLAMA_MTP_GPU_CHAIN_MULTI=1`, `LLAMA_MTP_GPU_CHAIN_UNROLLED=1`, `LLAMA_MTP_GPU_CHAIN_UNROLLED_DEPTH=2`, and `LLAMA_MTP_FIXED_PREFIX_ROWS=6`; keep the `n_rs_seq=4` runner policy. Require runtime logs to show `fixed-prefix pad enabled lanes=2 rows=12 outputs=2`, `single-graph path armed lanes=2 depth=2`, and `unrolled graph active lanes=2 depth=2` for both banks.

## Quality and state-isolation gates before model/performance work

1. Extend only the pure CPU fixed-prefix planner test for 2, 3, and 4 lanes. Verify interleaved source rows map lane-major to `6 × lanes` rows, one real seed output per lane, exact seed-backed padding, stable replay planning, and all existing rejection/rollback cases.
2. Use the existing `dual-context-runner.cpp` with a four-request, `dual=true` scenario (two requests per bank), each request carrying an exact expected output. Run generic baseline and candidate with the same binary/runtime/model and compare per-request generated token IDs and semantic outputs exactly. The runner already records bank/id, tokens, emitted times, draft proposals/accepts, and refuses subsequent performance scenarios if semantic gates fail (`:301-326,357-395`).
3. Add scenarios that swap request-to-bank assignment and that reset/reuse both banks. The runner's `bank::reset()` synchronizes each target/draft context, clears each memory independently, resets per-sequence carry, and clears lanes (`:93-103`). Verify output identity stays attached to request IDs and no bank's carry/KV state changes another bank's result.
4. Exercise unequal per-lane catch-up lengths 0..5, maximum prefix budget, and at least one forced planner/graph rejection. Confirm fallback restores the original batch and returns exact generic-MTP tokens; no padded future row may be sampled or left in KV. Compare accepted output token IDs after target verification, not just MTP draft proposals.
5. After correctness passes, only then record the candidate activation logs and compare direct step timings. This note is source readiness, not performance or model-level parity evidence.

## Evidence boundary

This audit is static. It neither builds the candidate nor proves that the new two/three-lane shape is semantically correct. The existing four-lane D2/D4 planner/allocator tests do not cover two or three lanes; the current P4 runner source uses two lanes per bank but does not enable unrolled fixed-prefix mode as currently gated.
